## embed

Responsible for splitting vault documents into overlapping text chunks and producing embedding vectors for each chunk. The chunker respects Markdown heading boundaries and the `ChunkerOptions` token budget; the embedding layer wraps `node-llama-cpp` (GGUF model) or a configured embedding API. There is no fake/hash fallback: without a real embedding provider the vector path fails loudly (ADR-005), while lexical BM25/FTS remains available. All output conforms to the `Chunk` and `EmbeddingProvider` contracts defined in `../types.ts`.

**Absorbed sources (idea-only, no verbatim code):**
- `nashsu/llm_wiki` (GPL-3.0) — sliding-window overlap heuristic and heading-aware split boundary detection.

Explicit maintenance uses `maintenance.ts` to replace one document and queue its embedding revision atomically in the existing SQLite store. It never creates a missing persistent store. The queue's random revision changes with each publication, so deleted and recreated notes cannot admit an old embedding result. `embedQueuedDocument` captures the raw Markdown chunk/title contract and configured model identity, releases the writer lock during inference, and conditionally publishes vectors after checking source evidence, chunks, queue revision, cancellation, and the caller's owner/configuration epoch. The caller owns the provider and verified-target admission. Missing or mismatched stored model identity requires explicit synchronization.

Maintenance validates the current owner/source and, for an inferred result, its captured queue revision, model identity, and chunks before initializing schema or vectors. This preflight and the subsequent publication use the same connection under an immediate SQLite transaction and the short writer lock. A later stale check rolls back initialization as well as data changes, so an old job cannot create its vector dimensions in a replacement lexical store or migrate a cancelled legacy queue. Maintenance preserves the existing journal mode.

These are SQLite transactions with optimistic filesystem revalidation, not atomic Markdown-and-database commits. A later filesystem change is reconciled by the owner or the next explicit sync. A failed or stale embedding job leaves its queue entry pending. Read-only queue/source inventory does not migrate schema; the nullable revision column is added only when an explicit writer opens the existing queue. Legacy lexical-before-queue failures are repaired by explicit embedding sync, which checks actual vector coverage even when the chunk SHA already matches. Lexical-only sync preserves existing pending entries.

After a successful complete scan, the owner can pass `purgeExcluded: true` to remove a previously indexed path that current exclusion policy excludes. The helper captures its source and queue revision, rereads exclusion policy before taking the writer lock, and checks source/owner again in the transaction. It also compares policy digests afterward; a changed policy returns `stale` even if deletion committed, requiring the owner to rescan. This is optimistic policy validation with the same filesystem-to-SQLite gap, not a cross-file compare-and-swap guarantee.

Short database writers use a separate immutable-record owner directory before entering the legacy `.lock` protocol. This prevents concurrent upgraded stale reclaimers from moving a live successor and admitting a third writer through the temporary pathname gap. The legacy lock remains visible as a compatibility courtesy; old processes do not observe the new owner directory, so mixed-version concurrent writers are not covered by this guarantee. Stop old writers before using the upgraded writer protocol. Unreadable or malformed legacy owner records block acquisition without moving or deleting them; only a valid, provably dead PID admits stale recovery.

Queued-job capture also handles interrupted queue housekeeping: a clean chunk set is dequeued only when source, model, and actual vector coverage all match. Otherwise verified current clean chunks are marked dirty again before inference. A legacy null revision is upgraded under that same guarded transaction, so old or partially drained queues do not cause endless stale-job retries.
